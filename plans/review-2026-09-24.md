# Review — 2026-09-24

A full pass over the repo at 0.5.0 against the brief and the design docs. The
verdict, the gaps, and recommendations for the structural items DJ asked about.
Decisions taken on the review are recorded at the bottom.

## Verdict

The architecture delivers what the brief asked for — sprawl by arithmetic — and
the hardest bet in the design, the actor graph inverting so an object leads to
a stocked room, is built and gated. The layer contract is real: one L4 system,
proven deletable by deletion, no sideways imports. 3,067 lines of game code,
zero dependencies, 297 headless gates.

But the game is one floor with two rooms on it, it cannot be saved, and the
perception system the design rests on has no progression behind it. **The
engine is ahead of the game.**

## Recommendations

### `visible()` is rebuilt ~5× per tick

**The problem.** `visible(s)` turns `s.taken` and `s.opened` — flat arrays that
grow for the life of a save — into fresh `Set`s on every call, and it is called
by `solidBodies` (in `step` and again in `combat`), `reachable`, `dropTile`, and
twice more from the renderer. Fine at a hundred taken items; at a few thousand
it is tens of thousands of insertions per tick on a phone.

**The solve, in two parts, and the first lands now.**

1. **One view per tick.** A `roomView(s)` that computes `{ visible, bodies,
   taken, opened }` once and caches it on the state under a transient field,
   valid while `(tick, site, floor, room, taken.length, opened.length,
   dropped.length)` is unchanged. Every mutation of those lists changes a
   length, so validity needs no invalidation calls. Consumers read the cache.
   This removes the redundancy: five rebuilds become one.

   It establishes a convention the save system needs anyway: **fields beginning
   `_` are transient** — never hashed, never saved, rebuilt on load. `foes`,
   `swing` and `say` are the same kind of thing and should join them.

2. **Room-keyed lists, if measurement warrants.** `taken` and `opened` could be
   maps from room address to a small list, so the current room's lookup never
   touches the rest of the world. This changes the save format, so it belongs
   before 1.0 and after a real number says it is needed. Not now.

### `sim/interact.js` is the load-bearing wall

*Resolved 2026-09-25: split into `room.js`, `carry.js`, `record.js`, `prompt.js`; the file is gone.*

It answers five different questions about the state — what is in the room, what
the toast says, what a thing is worth, what you swing with, what you can carry —
and every other file leans on it. Not a layer violation; L3 simply has no
internal structure.

**Split by question**, when equipment lands (it touches the same functions):

| Module | Answers |
|---|---|
| `sim/view.js` | What is in this room: `visible`, `roomView`, `reachable`, `containerItems`, `dropTile` |
| `sim/prompt.js` | What the toast says: `prompt`, `stationAt`, `stairUnder` |
| `sim/worth.js` | What a thing is worth and where it points: `chainFor`, `assessed`, `itemValue`, `leads`, `troveFor` |
| `sim/arms.js` | What you fight with: `weaponOf`, `hitBox`, `mostFragile`, and the equipment slots |
| `sim/bulk.js` | What you can carry: `carriedBulk`, `tier`, the budget and grid constants |

**The rule that stops it re-accreting:** a file in `sim/` answers one question
about the state. `interact.js` answered five.

### Every suite runs one seed

Five suites, one constant, `0x1594` five times. The "varies along seed" gates
prove variation exists; nothing proves the other 290 behaviours hold on a
different world.

**Parameterise, and sweep before a tag.** Each suite reads `process.env.SEED`
with `0x1594` as the default so the fast path is unchanged. `./check.sh --sweep`
runs every suite over a fixed list — `[0x1594, 0x0001, 0xdead, 0xbeef, 0x7fff,
0xcafe, 0x1234, 0x0bad]` — fixed rather than random so a failure reproduces.
Cost: eight times the runtime, only when asked. A seed that fails gets added to
the list permanently, which is the golden-transcript discipline for worlds.

### `pagecheck.html` is 486 lines of test in a page

Sixty-seven assertions, one file, the only thing that checks rendering, and the
hardest file in the repo to read.

**Thin page, modules of gates.** `tools/page/*.js` — one per concern (boot,
light, screens, input, replay) — each exporting `async function gates(ctx, ok)`.
`pagecheck.html` becomes forty lines: build the harness, import the modules in
order, run them. A gate module can then be read, diffed and blamed like any
other file, and a headless driver could run the same modules later without the
page at all.

### Docs outweigh code, 3,462 to 3,067

Not a defect. The case-study log is a stated deliverable and it has paid for
itself repeatedly. But entries have grown from ten lines to forty, and the
CHANGELOG now restates much of what the log already says.

**Three small habits, no restructuring:**

1. **A one-line lesson at the top of each log entry**, so the log is skimmable
   without being read. The lesson is the part that transfers.
2. **The CHANGELOG stays terse and points at the log.** Two sentences per
   entry; the argument lives in one place.
3. **Roll the log by month** — `case-study-log/2026-09.md` — once it passes a
   thousand lines. The current file is one entry short of that.

The ratio corrects itself as the game grows. The risk to watch is the log
becoming write-only, and habit 1 is the guard against that.
